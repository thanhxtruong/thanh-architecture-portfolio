ERP integration / Failure containment · Recovery

Following a silent failure four levels deep

Four fixes, each one assuming the failure was contained—and each one wrong about where the boundary actually was.

My contribution

Investigated the cascading failure and implemented changes to timeout configuration, recovery scope, per-entry scope, and batch containment.

In this case
  1. The system and the symptom
  2. Where the failure travelled
  3. The decision and its limits

The system and the symptom

An outbox dispatcher delivered subscription writes to an external ERP. Creating a contract was an irreversible, billable operation. A separate event-driven path also received ERP notifications and updated local records.

A contract existed externally, but the local application had lost the identifiers that proved it. Following the recovery path exposed how one failure could escape into the rest of the batch.

Where the failure travelled

Reading the evidence

This diagram summarizes the reconstructed propagation path. It does not establish timing, frequency, or production impact for each layer.

The decision and its limits

Recovery needed a fresh persistence scope, and each entry needed its own scope and failure boundary. Catching an exception alone did not make the shared context safe to reuse.

The lesson was to inspect the next enclosing boundary after every fix: what state remains changed, who reuses it, and what happens to the next item?

ERP integration / Timeout semantics · Correlation

Two causes behind a silent data gap

The external contract existed. The original local record had no identity for it. Both processing paths appeared to have done their jobs.

At stake

Recovering local truth without repeating an irreversible external write.

A timeout left the outcome unknown

The application asked an external system to create a contract. A per-attempt timeout expired before a response arrived, even though the external operation had succeeded.

The application treated this as failure. What it actually knew was narrower: it had not received confirmation.

Two paths could no longer find the same record

An asynchronous notification carried the external identifier. But the original local record never received that identifier, so the notification path could not correlate the result with the original request.

When a retry later recovered the identifier, a duplicate record already held it. Local persistence failed even though the external contract was real.

Recovery needs its own boundary

Repeating an external operation and repairing a local record are different actions. The investigation exposed why the recovery design needed to distinguish them.

Remaining uncertainty

Increasing a timeout can reduce how often this happens. It cannot remove the possibility of external success without a received response.

Architecture / Decision-making

A decision record and a system map answer different questions.

One preserves the reasoning behind a choice. The other helps someone understand the system they have today.

Article preview · Adapted from the existing ADR note

“Why did we choose this?”

A decision record captures the context, alternatives, and consequences of a particular choice. Its value lies in preserving what was known when the choice was made.

If a later decision changes the approach, a new record can explain the change and link back to the earlier one. The reasoning remains available to the next person who asks the same question.

“How does this work now?”

A system overview has a different responsibility. It should help a reader locate the current boundaries, dependencies, and processing paths. As the implementation changes, the overview needs to change with it.

A useful distinction

Preserve the history of decisions. Keep the description of the current system current.

Connect the two

A system map can link a surprising boundary to the record explaining why it exists. A decision record can link to the current overview, so readers can see what the system became.

This gives someone both an accurate starting point and a way to investigate the reasoning behind it.

Distributed systems / Failure & recovery

A timeout tells you less than you think.

Your application stopped waiting. The system on the other side may still have finished the work.

Article preview · Proposed writing derived from the case studies

Separate observation from outcome

A timeout is an observation made by the caller. It tells you a response did not arrive within a deadline. It does not, by itself, tell you whether the remote operation ran, failed, or succeeded.

The design question

If the first request succeeded, what would happen if we sent it again?

Choose a recovery action deliberately

For a state-changing operation, recovery may require checking the operation's status, reusing an idempotency key, or reconciling local state with the external system. The available choice depends on the remote API's guarantees.

A longer timeout may reduce uncertainty in normal conditions, but it cannot eliminate lost responses.

Follow the problem into a real system

The silent data gap case follows this uncertainty across a request path and an asynchronous notification path. It shows how a missing response becomes a correlation problem.
